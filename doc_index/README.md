# doc_index — 문서 색인·검색 컴포넌트 (키워드 + 벡터)

[`doc_chunker`](../doc_chunker/)가 자른 단위를 SQLite 파일 하나에 색인하고 찾습니다.
**키워드**(한국어 2글자 단위 BM25) · **벡터**(Qwen3-Embedding 등 OpenAI 호환 임베딩) · **혼합**(순위 결합 RRF).

## 설치·사용

```bash
PY=python
$PY -m pip install --config-settings editable_mode=compat -e ../doc_parser -e ../doc_chunker -e .    # 이 폴더에서 (doc_reader README)

$PY -m doc_index build 자료폴더/ --db idx.sqlite --embed-url http://<WSL IP>:8011/v1   # 없으면 키워드만
$PY -m doc_index search "출장 일비" --db idx.sqlite --embed-url http://<WSL IP>:8011/v1 [--mode keyword|vector|hybrid] [-k 10]
$PY -m doc_index stats --db idx.sqlite
```

```python
from doc_index import Index, OpenAICompatEmbedder, files_of
idx = Index("idx.sqlite", OpenAICompatEmbedder("http://<ip>:8011/v1"))
rep = idx.build(["자료폴더/"])            # 증분: 바이트가 같은 파일은 다시 읽지도·임베딩하지도 않음, 사라진 파일은 삭제
hits = idx.search("하우징 금형 비용", k=20) # Hit(unit_id, path, score, text, loc, ranks={"keyword": 3, "vector": 1})
files_of(hits)                            # 파일 순위 (파일은 가장 좋은 단위의 순위)
```

임베딩 서버: OpenAI 호환 `/v1/embeddings` (Qwen3-Embedding 기준으로 측정 — vLLM 또는 CPU 서버). 작성자 PC에서는 다른 프로젝트의 CPU 임베딩 서버(:8011)를 같이 씀.

## 화면·A2A

자료실 검색·자료 관리 화면과 A2A 기능 `search-documents`·`add-folder`는 [doc_reader](../README.md) 서버에 있습니다 (`/library/`).
이 패키지의 `service.py`(자료실 데스크: 자료 폴더·색인 작업·검색, 색인 DB는 WAL)를 그 서버가 씁니다. 임베딩 서버가 꺼져 있으면
키워드로 찾고 키워드만 색인하며, 벡터 없는 단위는 서버가 켜진 다음 색인에서 채웁니다.

## 키워드 처리 (`doc_index/text.py`)

- 한글은 2글자씩: `출장비는` → 출장·장비·비는 (2음절 단어·조사 붙은 말도 맞음)
- 영문·숫자는 한 덩어리, 안쪽 기호 제거: `NS-500` → `ns500`, `v2.1` → `v21`, `14,000` → `14000`
- Word PDF의 숫자-한글 공백 제거: `제12 장` → `제12장`
- 숫자 바로 뒤 한글은 묶음 토큰도 추가: `3분기` → 3 · 분기 · **3분기** (기간이 정확히 맞는 문서가 위로 — 2026-11-13 추가)

토크나이저를 바꾸면 `Index.reindex_keywords()`로 키워드 색인만 다시 만든다(벡터는 그대로).

## 같은 계열 문서 (`Index.family`)

파일명에서 날짜·분기·버전·상태어(구버전·확정·잠정·초안)·앞 번호를 지운 이름이 같으면 같은 계열.
`family(path)`는 같은 계열의 다른 파일을 **최신순**으로 돌려준다
(`출장비규정_v1.0` → `08_출장비규정_v2.1`, `07_…v2.0_구버전` / `주간회의록_2026-09-07` → `…10-20`, `03_…10-06`).
검색이 구버전을 높게 올려도 최신본을 옆에 놓고 비교하게 하려는 용도. 이름이 다르게 붙은 계열(`실적_…` vs `영업실적_…`)은 못 묶는다.

## 측정 (2026-11-13, `tools/`)

시험 묶음: 정답 12개 + 비슷한 오답·일반 문서 1,956개 = 1,968개 파일(중복 182 제외 1,786 단위). 질의 23개
(시나리오 10 · 다른 표현 8 · 번호/숫자 5), 정답·함정(구버전·잠정본)은 `tools/queries_nurisense.json`.
"LLM 검색어"는 Qwen3.8-27B가 요청마다 만든 검색어 3~5개(`tools/rewrite_queries.py`, 요청당 4.4초)를 원 질의와 함께 검색해 순위 결합.

| 방식 | R@5 | R@20 | 필요 문서 전부 상위 20 안 | MRR | 함정이 정답보다 위 |
|---|---|---|---|---|---|
| 키워드 | 0.80 → 0.71 | 0.81 → 0.82 | 0.78 → 0.78 | 0.66 → 0.61 | 6 → 7/11 |
| 벡터 | 0.69 | 0.74 | 0.70 | 0.49 | 5/11 |
| 혼합 | 0.75 → 0.78 | 0.82 → 0.82 | 0.78 → 0.78 | 0.62 → 0.59 | 5 → 6/11 |
| 키워드 + LLM 검색어 | 0.60 | 0.92 | 0.91 | 0.40 | 5/11 (변경 후 미측정) |
| **혼합 + LLM 검색어** | 0.66 → 0.66 | 0.93 → 0.90 | 0.91 → 0.87 | 0.44 → 0.45 | 4 → 4/11 |

화살표: 숫자+한글 묶음 토큰 추가 전 → 후 (둘 다 2026-11-13 측정). 묶음 토큰의 목적이던 "이사회 보고용 3분기 주요 이슈"의
3분기 VOC는 90위 → 18위로 올랐지만, 다른 질의 1개가 상위 20 밖으로 밀렸다 — 23개 질의에서 1개 차이라 전체 우열은 판단 보류.

읽는 법
- 번호·숫자 질의는 키워드가 전부 1위. 표현이 다른 질의는 키워드·벡터 모두 일부 못 찾고("겉케이스 틀" → 하우징 금형), LLM 검색어가 보완
- LLM 검색어는 **넓게 건지기(상위 20)를 올리고 상위 5의 정밀도를 낮춤** → 뒤에서 LLM이 후보 20~30개를 보고 고르는 구조에 맞음
- 구버전·잠정본은 검색만으로 걸러지지 않음(모든 방식에서 4~6/11이 정답보다 위). 둘 다 건진 뒤 단위 머리의 시행일·버전·상태로 고르는 일은 다음 단계(자료 지도)
- 남은 실패: "이사회 보고용 3분기 실적과 **주요 이슈**" — VOC·파일럿 일정표는 요청에 단서가 없음. 회의록을 먼저 읽어야 알 수 있어 **읽고 다시 찾는 반복(에이전트 검색)** 이 필요
- 한계: 오답 문서가 틀(template)로 생성돼 어휘가 반복됨 → 키워드에 유리한 묶음일 수 있음. 실제 문서로 다시 재야 함
- 비용: CPU 임베딩 1,786 단위 513초(초당 약 3.5). 키워드 색인 21초. 검색 요청당 키워드 0.06초 · 혼합 0.2초 · 혼합+LLM 검색어 1.2초(LLM 생성 제외)
